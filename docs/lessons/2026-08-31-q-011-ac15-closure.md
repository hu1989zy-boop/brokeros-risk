# Q-011 AC15 Closure — Migration-Count Test Maintenance

## Context

Q-011 Acceptance Criterion 15 remained open because the unchanged Q-009 real-
MySQL integration test established a V1 baseline and then hard-coded that one
additional migration would execute. That assumption was already stale after
Q-010 added V3 and observed three pending migrations once Q-011 added V4.

The Product Owner authorized a narrowly scoped maintenance change to
`Q009MySqlIntegrationTests.java` only. No Q-009 production code, Q-010/Q-011
file, or V1–V4 migration was changed. The separate Q-010 bootstrap replay
timestamp-precision finding remained explicitly deferred.

## Fix

After the V1-only baseline is established, the test now reads
`flyway.info().pending().length` before full migration and compares
`migrate().migrationsExecuted` with that dynamically derived count. All
subsequent schema, constraint, query-plan, adapter, lifecycle, restart, and
validation assertions remain unchanged.

## Reusable Pattern

Tests that intentionally validate an older Flyway baseline followed by all
currently available additive migrations must not hard-code the number of later
migrations. Derive the expected count from Flyway's pending migration metadata
immediately before migration, then assert the executed count against that
snapshot. This preserves the test's real purpose while allowing future approved
migrations to be added without unrelated historical-test maintenance.

Hard-code a migration count only when the exact count is itself the governed
contract being tested, such as an isolated target-version transition with a
fixed approved endpoint.
